# Архитектура

## Общая схема

```
                    ┌──────────────── nginx (gateway) ────────────────┐
  browser ────────► │  /        → web          (статика SPA)          │
                    │  /api/*   → core-api     (Java)                 │
                    │  /ai/*    → ai-service   (Python, SSE-стриминг) │
                    └─────────────────────────────────────────────────┘
                              │                         │
                              │   internal HTTP         │
                              │ ◄─────────────────────► │
                              ▼                         ▼
                     ┌──────────────────────────────────────┐
                     │ PostgreSQL                           │
                     │   schema core  ← только core-api     │
                     │   schema ai    ← только ai-service   │
                     └──────────────────────────────────────┘
                                                        │
                                                        ▼
                                         RouterAI  /  своя модель (позже)
```

У браузера одна точка входа — nginx. Благодаря этому нет проблем с CORS, а
фронт обращается к относительным путям `/api` и `/ai`.

## Зоны ответственности

### core-api (Java)
- Регистрация, логин, refresh-токены.
- **Единственный, кто выдаёт JWT.** Подпись RS256, публичный ключ
  публикуется на `GET /api/.well-known/jwks.json`.
- Пользователи и профили (уровень, стек, целевая позиция).
- Собеседования как бизнес-сущность: создание, статус, итоговый результат,
  история.
- Всё остальное «обычное» — пусть живёт тут.

### ai-service (Python)
- Ведение диалога собеседования с LLM, стриминг ответов (SSE).
- Хранение переписки (schema `ai`).
- Оценка ответов кандидата и итоговый фидбек.
- Промпты и сценарии собеседований.
- **Не выдаёт токены**, а только проверяет JWT по JWKS из core-api.
- Ничего не знает о паролях и регистрации.

### web (React)
- SPA. Access-токен хранится в памяти, refresh-токен — в httpOnly cookie.
- Типы API генерируются из `contracts/`.

## Ключевые потоки

### Логин
```
web ──POST /api/auth/login──► core-api ──► { accessToken } + refresh cookie
```

### Собеседование
```
1. web ──POST /api/interviews──────────────► core-api     создаёт интервью (status=CREATED)
2. web ──POST /ai/interviews/{id}/messages─► ai-service   (Authorization: Bearer <jwt>)
       ◄──────── text/event-stream ─────────              токены ответа LLM стримом
3. ... повторяется ...
4. web ──POST /ai/interviews/{id}/finish───► ai-service   считает оценку
       ai-service ──PUT /internal/interviews/{id}/result─► core-api   сохраняет результат
```

Стриминг идёт **напрямую** во фронт через ai-service, а не через Java:
проксировать SSE через второй сервис — лишняя сложность.

## Межсервисное взаимодействие

| Откуда → куда | Как | Авторизация |
|---|---|---|
| web → core-api | REST `/api/*` | JWT пользователя |
| web → ai-service | REST + SSE `/ai/*` | JWT пользователя (проверка по JWKS) |
| ai-service → core-api | REST `/internal/*` | сервисный токен `INTERNAL_API_TOKEN` |
| core-api → ai-service | пока не нужно | — |

Эндпоинты `/internal/*` **не проксируются** через nginx и доступны только
внутри docker-сети.

## Данные

Один экземпляр PostgreSQL, но у каждого сервиса **своя схема и свой
пользователь БД**. Ходить в чужую схему запрещено, нужные данные получать
через API. Тогда сервисы можно разнести по разным базам без переписывания.

- `core`: users, refresh_tokens, interviews, interview_results
- `ai`: messages, prompt_versions, evaluations

Миграции: core-api — Flyway, ai-service — Alembic.

## Расширяемость LLM

В ai-service весь доступ к модели идёт через интерфейс `LLMProvider`
(`chat`, `stream`). Реализации:
- `RouterAIProvider` — сейчас;
- `LocalProvider` — потом, для своей дообученной модели.

Провайдер выбирается переменной `LLM_PROVIDER`. Обучение модели живёт в
`ml/` и в рантайм-сервис не попадает.

## Контракты

`contracts/*.yaml` — источник правды для API. Порядок работы:
1. Меняем спеку в PR.
2. Бэкенд реализует (или генерирует интерфейсы).
3. Фронт перегенерирует клиент: `make api-gen` (Orval: хуки React Query, типы, MSW-моки).

## CI (когда появятся проекты)

Отдельный workflow на каждый сервис с фильтром `paths:` — изменения во
фронте не гоняют тесты Java и наоборот.
